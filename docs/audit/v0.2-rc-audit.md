# v0.2 release-candidate audit

**Scope.** The Trusted Core on `main` at `30f8453`: v0.2 (steps 1–10), plus v0.3 steps ① and ②. The audit follows the whole physical-authority path:

```text
untrusted AI → intent / plan / lease → identity + delegation → Authority → Safety → approval
  → Trusted Execution Boundary → ExecOrder → executor / adapter → receipt → witness → outcome
  → recovery → audit / persistence / restart
```

**Goal.** Try to break it. No new features: gaps are fixed with regression tests, nothing else. Crash/restart and unknown physical executions came first (Project Lead, 2026-10-05).

**Method, for every suspicion:**

1. A red test that proves the gap before any fix.
2. The smallest fix.
3. A regression test.
4. Mutation: the fix is reverted on purpose, and the test must fail.

On top of that, the audit used:

- a seeded property test of random faults, crashes and restarts;
- a multi-threaded stress test;
- repeated runs to rule out flakiness.

## Findings

| Id | Severity | Finding | Status |
|---|---|---|---|
| H1 | High | A command whose outcome was still pending (reported or unknown) was forgotten at a restart: pending outcomes lived in memory only. After a crash, Chitala could lose the knowledge that a door lock may have been unlocked | **fixed** |
| H1b | High | The fix's write-ahead record could fail to reach the disk and the order still left the node: `save_state()` only audited a write failure and carried on | **fixed** |
| H2 | Medium/High | SAFE-7 (one action at a time) locked devices, not resources. A resource bound to two devices (a bolt thrown by one controller, withdrawn by another) took two interleaving orders, and each judged its outcome against the other's effect | **fixed** |

### H1: uncertainty did not survive a restart

- **Proof.** `home_assistant::an_unknown_execution_survives_a_restart` was red. After the restart there were zero pending outcomes, and the door was not in recovery.
- **Fix: a write-ahead record in the persisted domain state** (`DomainState.inflight`, spec 22 "Uncertainty survives the node"):
  1. reserve before the decision record, with an epoch bump;
  2. persist the order id after minting and before the order can leave;
  3. remove the entry when the outcome settles or the execution certainly did not happen;
  4. at start-up, watch every minted entry again, and drop the entries never minted.
- **Why the epoch.** The decision record and its context carry the bumped epoch, so a state file rolled back past the reservation is refused at start-up. The context digest stays recomputable from the record.

### H1b: the write-ahead record must be durable or nothing happens

- **Proof.** `node::memory_platform::an_action_whose_record_cannot_be_written_never_executes` was red: the door unlocked although its record could not be written. The test uses a new write-fault injection in the memory platform (`fail_writes`, `fail_writes_after`).
- **Fix.** `persist()` reports failure.
  - A failed reservation: the action is refused with `X_INTERNAL` ("not executed").
  - A failed order-id write: the minted order is dropped before it leaves ("not sent"). The order id is persisted before the device and the resource are marked busy.
- **Contract (spec 18).** `write_atomic` returning `Ok` means durably and atomically committed. The hosted backend does this with a temporary file, `sync_all` (F_FULLFSYNC on macOS), rename and a directory sync.

### H2: one resource, two devices

- **Proof.** `audit::one_resource_through_two_devices_takes_one_action_at_a_time` was red: a lock through one controller was allowed while an unlock through the other was still executing.
- **Fix.** SAFE-7 also locks the **exact resource** an executing order acts on (`Proposed.resource_busy`, `Node.busy_resources`).
- **Guard against over-locking.** Neighbours and enclosing spaces are not locked. `audit::resources_that_share_a_room_do_not_wait_for_each_other` stays green.
- **Under real concurrency.** `audit::one_door_two_controllers_many_clients_never_two_orders_at_once` drives one door with 8 threads through two adapter host instances via the node's IPC entry point. The peak of concurrent executions on the door is 1. Without the fix it reaches 2, in 3 of 3 runs.

## Testing beyond single features

- **Seeded property test.** `home_assistant::random_faults_crashes_and_restarts_keep_every_invariant` runs random sequences of:
  - lock and light commands;
  - nine Home Assistant fault behaviours (lost answers with and without an effect, death after sending, stuck, slow, dropping off, refused and failed calls);
  - crashes at points C and D, and plain restarts;
  - outages and returns, and time passing.

  After every run it checks that:
  - Home Assistant never received more commands than orders were minted (nothing is sent twice);
  - after quiescence, nothing is pending and nothing is in flight;
  - **every order caught by a crash was judged exactly once after the restart**;
  - the door is in recovery exactly when some door promise of medium risk or more was broken or could not be established.

  The default is 12 seeds in CI; 150 seeds were run locally, all green. Mutation check: a restart that forgets its records fails at seed 1, with the operation sequence printed.
- **Mutation.**
  - The fixes: ignore a failed reservation write, ignore a failed order-id write, do not lock the resource. Each made the suite fail.
  - The earlier steps were also mutation-checked when they were written: 8 faults for the Home Assistant adapter (PR #25) and 5 for recovery under unknown executions (PR #25).
- **Repetition.** The audit, Home Assistant and node suites ran 20 times in a row, all green.

| O1 | SAFE-7 locks the exact resource only. Physical coupling between *different* resources (two doors of one airlock, a gate and its motor modelled as two resources) is not modelled; locking whole subtrees would over-serialise unrelated things. Modelling coupling explicitly is a design decision | Project Lead |
| O2 | The Home Assistant adapter treats `not_found`, `invalid_format`, `service_validation_error`, `unauthorized` and HTTP 4xx as "did not run". Verify each against a real Home Assistant | v0.3 ③A |
| O3 | The Native platform is a lab tier without persistent storage across boots (spec 13 N8). The write-ahead contract holds per the storage trait; a production Native node needs durable storage first | Native track |
| O4 | Every physical action now writes the state file up to three times (reserve, minted, settle). This is fine for a home node; revisit if v0.3 load measurements say otherwise | v0.3 |
