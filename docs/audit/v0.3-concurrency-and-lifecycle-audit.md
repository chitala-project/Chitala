# v0.3 concurrency and lifecycle audit

**Scope.** The whole codebase on `main` at `2a9a9ff` (2026-10-06): about 56,000 lines of Rust in 19 crates, plus the native spike. Every crate forbids `unsafe`.

**Question.** Does Chitala leak memory or other resources, and does it have race conditions: anything whose result depends on how threads, processes or answers interleave?

**Method.**

- **A static review** of:
  - every collection in a long-lived structure, and what bounds it;
  - every thread, process, channel and file handle, and what ends it;
  - every lock and the order in which locks are taken;
  - every write that must be atomic.
- **Deterministic probes for each suspected race.** A probe interleaves the steps through the public API, exactly as the IPC server's threads can, so nothing depends on luck.
- **A heap soak.** A counting global allocator tracks live bytes and a histogram of live allocations by size class. It ran 60,000 rounds of mixed requests (owner commands with outcome verification, reads, denials, garbage, delegations, ticks), with the audit log stored on disk as in production.
- **ThreadSanitizer** (nightly, `-Zbuild-std`) over the concurrency-heavy suites.
- **The lab's resident memory** after hours of regressions.

Each finding followed the same path:

1. a red test that proves it;
2. the smallest fix;
3. regression tests;
4. mutations: the fix is reverted on purpose, and the tests must fail.

The Project Lead granted a core-freeze exception for the four fixes (2026-10-06): they restore correctness and security invariants and add no features.

### R1: an order the host took has an unknown fate when the host fails

- **Proof.** A scripted adapter host took an `execute`, then exited, or hung past the timeout. The node answered `X_DEVICE_UNAVAILABLE`, with no outcome. The existing test `hung_adapter_host_does_not_stall_the_node` asserted exactly that.
- **Fix.** The executor's transport failure says whether the request line had been written to the host (`Transport { why, taken }`). A taken order that fails is `X_EXECUTION_UNKNOWN`: outcome verification watches it, recovery follows when nobody can establish the result, and nothing is sent again. `X_DEVICE_UNAVAILABLE` stays for an order that never reached the host.
- **Tests.**
  - `an_adapter_host_that_takes_an_order_and_dies_leaves_its_fate_unknown`:
    - the light: watched, `not_applied` once observed again, never resent;
    - the door: nothing can be observed afterwards, so `unconfirmed` and recovery.
  - The hung-host test is now an R1 regression.
  - The garbage-host and stale-order tests cover garbage after a taken order, and the order a dying instance swallowed.
- **Mutations:** 6 of 6 caught.

### R3 / R3b: causal order of observations

- **Proof.** The node observes devices outside its lock and folds each answer in later. Through `due_observations`, `Observer::run` and `observed_by`:
  - **R3:** a reading of the door taken before an unlock and folded after it turned the twin back to `locked`;
  - **R3b:** a good reading taken before a failed one and folded after it cleared `unobservable_since`, and the offline door looked fresh.
- **Fix.**
  - **Stamping on arrival.** Every adapter answer is stamped as it arrives with `Received { at_ms, seq }`: the node's time, plus a sequence that every path shares.
  - **One lane per device.** Answers about one device go through their own lane, and each is stamped under the lane's lock. So for each device the stamps follow the order the device answered, however the threads are scheduled afterwards. The adapter host already serves one request at a time, so this costs no concurrency.
  - **The twin applies only later answers.** It applies an answer only if it is later than the last one it applied, good or failed (`Stale` otherwise).
  - **A rejected answer is no outcome evidence.**
- **Tests:**
  - three red tests (an earlier reading, an earlier good reading, an earlier failure, each folded late);
  - an outcome test through Home Assistant;
  - a unit test with 8 threads and 200 answers at random delays;
  - a twin unit test with ties within one millisecond.
- **Mutations:** 7 of 7 caught.

### F11: evidence belongs to the answer that gave it

- **Proof.** Through the fake Home Assistant, a live Matter lock:
  1. confirmed locked after an unlock whose answer was lost;
  2. then reported `unlocked` and died.

  The outcome ended `not_applied` with `observed {locked: true}` and no recovery. With a reported execution, the same flaw gave a false `diverged`.
- **Fix.**
  - A pending outcome's evidence keeps the answer it came in.
  - A newer answer that is no evidence itself, and states another value (or no value) for a promised key, takes the evidence away.
  - A newer answer of the same fact keeps it, and keys the action did not promise do not count.
- **Tests.**
  - The red test now ends `unconfirmed` with recovery.
  - The same-fact case keeps `not_applied`.
  - The reported case ends `unconfirmed`, not `diverged`.
  - A unit test with two promised keys.
- **Mutations:** 3 of 3 caught. The generation guard (`seen_seq < seq`) cannot be reached today, because R3 makes answers arrive in order. It stays for future callers.

### R2: one node per domain

- **Proof.** With the binary, a second `chitala node` on a running domain was refused at the socket. By then it had already appended to the audit log. `audit verify` then failed ("corrupt or tampered at line 5"), and the running node refused to restart.
- **Fix.**
  - **The PAL gains `Storage::claim`.** It is an exclusive claim that ends with its guard or its process:
    - hosted: an advisory `flock` on a private file, released by the kernel even after a crash;
    - memory platform: a claim set.
  - **`start_node` claims `<state_file>.lock` before anything else** — before adapter hosts, the state and the audit log — and the node holds the claim for its life. A second node stops at once, having written nothing.
- **Tests.**
  - The memory-platform red test: the audit log and state stay byte-identical, no adapter host starts, and the domain restarts after the first node stops.
  - A cross-process test: perl holds the `flock`, so the claim is refused; perl is killed, and the claim succeeds.
  - The storage contract on every backend.
  - The binary scenario, repeated: refused, `audit verify` passes, the first node restarts.
- **Mutations:** 6 of 6 caught.

### F10: the order of a Matter interview and Home Assistant's state

Found while closing F9b. The details are in the lab report ([`v0.3-step3a-home-assistant.md`](../lab/v0.3-step3a-home-assistant.md)).

| Situation | Rounds | Bad |
|---|---|---|
| Normal operation, state changed −40 to +60 ms around the interview | 80 | 0 |
| Two concurrent interviews | 40 | 0 |
| **Induced backpressure on the Matter server's connection to Home Assistant** | 6 | **3**: the interview succeeded while the client still held the old state |
| Matter server killed during an interview | 3 | 0: no answer, so Chitala times out and confirms nothing |

Home Assistant's `matter/interview_node` returns no data, and no fence through Home Assistant is sound. The Matter server's `read_attribute` does a real Read of the device and returns the values (3–10 ms in the lab). The Project Lead chose a narrow `MatterEvidenceProvider`:

- read-only;
- an allowlist of clusters and attributes;
- no invoke, write, commission, fabric management or passthrough;
- loopback or an equally isolated transport only, because the Matter server's API has no authentication.

It is a bridge toward step ⑤, not a new core abstraction. It has since been built, and Home Assistant's state of a Matter device is never evidence now.

## What was checked and found sound

These negative findings bound what the audit covered.

- **No unbounded growth in the node.**
  - The heap soak plateaued once the bounded caches filled. The size histogram showed the only growing allocation was the replay cache's table (32-byte buckets), which stops at its cap.
  - In the lab, the node used 11.5 MB of resident memory after 8 hours of regressions; the adapter hosts used 4.8 MB and 2.9 MB.
- **ThreadSanitizer: 136 tests, no reports.** The suites covered:
  - the node's audit, IPC and isolation, Home Assistant and outcome suites;
  - the adapters' Home Assistant link against the fake;
  - the event bus.

  With `unsafe` forbidden, data races in Chitala's own code are ruled out by the compiler. TSan checks the dependencies and the standard library under our load.
- **No lock-order cycle.**
  - The node lock is taken before the authority view.
  - Device work outside the node lock only reads the view.
  - The bus always takes subscribers, then a queue.
  - The adapter host link, the Home Assistant link cache and the trusted clock take no other lock while holding their own.
  - The new device lanes are never held while the node lock is taken.
- **IPC.** Connections are bounded (`MAX_CONNECTIONS`), with read and write timeouts and line limits. The connection counter is released by a guard, even on panic.
- **Processes.**
  - Adapter hosts that stop are killed and waited for: no zombies.
  - Reader threads end at EOF.
  - Respawns are rate-limited on the monotonic clock.
- **Files.**
  - The state file is written atomically: temporary file, `sync_all`, rename, directory sync.
  - The audit log is appended and synced, and never held in memory in production.
- **The rate limiter and containment** count verified principals only (authenticated, non-person), so unknown actors cannot grow their tables.
- **Event bus.** Subscribers are weak references with bounded queues.
- **Adapters.** The order gate's replay set is bounded (10,000). The Home Assistant link's pending calls are answered or expire, and its caches cover the watched entities only.
- **A poisoned node lock fails closed:** the node refuses every request until it is restarted.

## Resources

None of these leaks without bound. The Project Lead's decisions (2026-10-06):

| Item | Decision |
|---|---|
| The monitor's replay cache (cap 100,000, about 6 MB) and the order gate's replay set (cap 10,000) prune only when full | bounded; not a priority |
| `RevocationList` is never pruned | not now: the retention semantics are not settled, and pruning wrongly is more dangerous than keeping |
| The audit log is read whole at start-up, so start-up memory and time grow with the log's age | later: checkpoint, index or segment verification rather than holding the history in memory |
| MCP reads stdin lines without a length limit | soon: a hard line cap, because it is a trust boundary |
| A poisoned node lock fails closed, but the process stays up, so a supervisor does not restart it | noted |
