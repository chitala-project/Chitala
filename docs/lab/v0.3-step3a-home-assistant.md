# v0.3 step ③A: a real Home Assistant, a real AI

**Date.** 2026-10-05.

**Code.** `main` at `66b9fb3` (v0.2.0 plus the CLI fix), then the fixes below.

**Question.** Does the chain hold when everything except the physical actuator is real?

```text
real AI (Claude, headless) → MCP → chitala-mcp → node: Intent → Authority → Safety → boundary → ExecOrder
  → adapter host → Home Assistant Core 2026.9.4 (WebSocket + REST) → Demo integration → witness → outcome
```

Step ③A does **not** complete step ③. Step ③B repeats this with physical devices, and the virtual Matter part of ③A comes separately. Chitala was not changed to suit the lab: every fix below is a defect that a real Home Assistant or a real AI exposed.

## Verdict

The chain held in all 21 scenarios on the real Home Assistant, 4 of them with a real AI. Six findings were made:

| | Finding | Severity | Status |
|---|---|---|---|
| F1 | Discovery proposed `light.set_brightness` for every light, also on/off-only ones | low | **fixed** |
| F2 | Home Assistant answers **success** to a call on an entity it does not have. Chitala stayed safe; a config typo shows only as `unconfirmed` outcomes | low | open: recommendation below |
| F3 | A real AI could not use a right delegated again: the MCP broker (and `chitala intent`) attached the first token naming the right, **expired or not** | medium | **fixed** |
| F4 | After its token was revoked, Chitala presented it about 6 times a second. Home Assistant counts each as a failed login, and with `login_attempts_threshold` set it **bans the address for good** | medium | **fixed** |
| F5 | The node observes a device whose last observation failed again on every tick (1 s), without backoff | low | open: Trusted Core, for the Project Lead |
| F6 | A device Home Assistant reports `unavailable` keeps its last state as **fresh**, and Safety admitted a high-risk unlock on it | medium | open: Trusted Core, for the Project Lead |

## Setup

- **Home Assistant Core 2026.9.4** in a Python 3.14 venv, with the Demo integration (lights, switches, four locks), listening on `127.0.0.1` only. The setup is reproducible from [`lab/home-assistant/`](../../lab/home-assistant/README.md).
- **The Chitala node** is the sample home of `chitala init`:
  - three devices go through Home Assistant as SC1, on two adapter hosts (Home Assistant and the virtual devices);
  - a back door is added on the Demo lock that jams.
- **Independent witnesses:**
  - Home Assistant's own `call_service` events, to count commands;
  - a logging proxy, for every request Chitala sent;
  - Home Assistant's log.
- **The real AI** is Claude Code run headless as the MCP client, with no tools but `chitala-mcp`, acting as `ai:assistant` for `person:alice`.

## Findings

### F1: discovery and brightness (fixed)

`chitala ha-discover` proposed `light.set_brightness` for every light. Home Assistant's rule is that a light dims when one of its `supported_color_modes` is not `onoff`. Discovery now follows it, and a light that declares no color modes is not assumed to dim.

- **Tests:** `discovery_proposes_brightness_only_for_lights_that_have_it`.
- **Mutations:** 3, all caught.

### F2: Home Assistant answers success for an entity it does not have (open)

A service call on a missing entity returns success over WebSocket, and HTTP 200 `[]` over REST, while nothing runs. This is why Chitala never takes "success" as the outcome. In the lab:

- a door mapped to a missing entity was refused by Safety, because its state is unknown;
- a light reached `unconfirmed`.

**Recommendation.** While the link is live and bootstrapped, Home Assistant's own states say whether an entity exists. The adapter could:

- refuse a command to a missing entity before sending it, which certainly does not execute it;
- report the typo plainly, instead of producing an `unconfirmed` outcome each time.

This changes the adapter's semantics slightly, so it is left for review.

### F3: the AI's token choice (fixed)

Alice delegated a right again after its token had expired. The AI was still refused "token expired", because the broker took the first token in the file that named the right. A request that no token named was refused "token expired" too, for the same reason.

**Fix.** The broker and `chitala intent` choose in this order:

1. a token valid now on the exact resource;
2. a token valid now on a scope;
3. the same two, expired or not valid yet;
4. any other token.

The full rule is in spec 12.

- **Tests:** four in `chitala-mcp/tests/broker.rs`, one in `chitala-cli`.
- **Mutations:** 7, all caught.

### F4: a rejected token presented again and again (fixed)

Home Assistant counts every request with a rejected token as a failed login. With `ip_ban_enabled` and `login_attempts_threshold` set, which is a common hardening, it bans the address and writes the ban to `ip_bans.yaml`. Only the Supervisor's address is exempt. The node observed every Home Assistant device once a second by REST, so a revoked token meant about six failed logins a second.

**Fix.** The link and REST share an `AuthGate`:

- it closes after a rejection (`auth_invalid`, or 401 on a read);
- it reopens after 5 s, doubling up to 10 min;
- in between, every request is answered at once with `X_ADAPTER`, and nothing is sent.

In the lab, through the proxy, the link presented the token at 0, 5, 15 and 35 s, and REST sent nothing.

- **Tests:** four in `ha_tests.rs`.
- **Mutations:** 7, all caught.

Home Assistant logged none of the link's failed logins. It answers `auth_invalid` first and only then records the failure, and the link closes the connection at once. Nothing should rely on that ordering.

### F5: failed observations are retried every second (open: Trusted Core)

`Node::due_observations` picks a device whose last report is older than half its allowed age. A failed observation records nothing, so the device is due again on the next tick, once a second. With the link live, this only costs REST reads for entities the link does not know, about one a second each, as F2's typos showed. Before F4 it was the token storm.

**Proposal.** After a failed observation, back off per device (for example 1 s doubling to 30 s), while witnesses of pending outcomes stay on the tick. Safety is not weakened: an old state is already refused by `SAFE-3`.

### F6: an unavailable device keeps a fresh state (open: Trusted Core)

Home Assistant reported the front door lock `unavailable`. Chitala's twin kept `locked: true` with freshness `fresh`, adding only an `observe_error`, and `SAFE-3` admitted Alice's unlock, a high-risk action.

- **What happened in the lab.** The Demo lock still worked, so the unlock ran and was `verified`.
- **What a real offline lock would do.** The command would fail or go unobserved, and outcome verification would put the door in recovery. The approval and the Safety decision would still rest on a state the newest observation contradicts.
- **The spec.** This follows spec 10 to the letter ("the previous view with `observe_error` and the matching freshness"). It is a gap in the design, not in the code.

**Proposal.** An observation that fails because the device reports itself unavailable makes the state **unknown** for Safety until a good observation arrives. The approver then sees "unknown", not "locked". This is a Trusted Core change, so it needs a decision.

## Audit item O2: closed

Every error the adapter takes as "did not run" was produced on the real Home Assistant over both transports. The entity was checked before and after each call, and nothing ran. The table is in [spec 25](../../specs/25-home-assistant-adapter.md), section *Checked against a real Home Assistant*.

Two cases are classified more cautiously than needed:

- a feature the entity lacks: REST answers HTTP 500;
- a read-only user: WebSocket answers `home_assistant_error` "Unauthorized".

In both, outcome verification then finds `not_applied`.

## Home Assistant facts worth knowing for ③B

- **The `http:` block is on trial.** Since 2026.9 it is moved into storage as a config on trial. Unless it is confirmed (`http/config/promote`) within five minutes, Home Assistant reverts to listening on every interface and restarts. The lab's bootstrap confirms it.
- **A Demo lock's call returns only once the lock has moved**, about 2 s later. Physical locks and their integrations may answer before the state changes. That is what `pending` and `within_ms` are for.
- **Running `hass` directly**, a restart is an exit with code 100, and something must start it again (`run_hass.sh`).

## What ③A does not show

- Physical devices, radios and their timing (③B).
- Matter (③A's virtual Matter devices, then step ⑤).
- Home Assistant over TLS (`https`/`wss`) or across a network: the lab used plain HTTP on loopback.
- An integration's own retries inside Home Assistant, which Chitala cannot see.

## A note on the AI

In scenario 14 the AI summarised the outcomes as "independently verified". The record says `independent: false`, because the witness is the device that acted. People should read Chitala's record, not the model's summary of it.
