# v0.3 step ③A: a real Home Assistant, a real AI, virtual Matter devices

**Date.** 2026-10-05.

**Code.** The first pass ran on `main` at `66b9fb3` (v0.2.0 plus the CLI fix). The fixes below followed, and the regression was run again on top of them.

**Question.** Does the chain hold when everything except the physical actuator is real?

```text
real AI (Claude, headless) → MCP → chitala-mcp → node: Intent → Authority → Safety → boundary → ExecOrder
  → adapter host → Home Assistant Core 2026.9.4 (WebSocket + REST) → Demo integration → witness → outcome
```

Step ③A does **not** complete step ③. Step ③B repeats this with physical devices. The second part of ③A puts virtual Matter devices from the Matter SDK behind the same Home Assistant (section *Matter*). Chitala was not changed to suit the lab: every fix below is a defect that a real Home Assistant or a real AI exposed.

## Verdict

The chain held in all 21 scenarios on the real Home Assistant, 4 of them with a real AI. Six findings were made, and all six are fixed:

| | Finding | Severity | Status |
|---|---|---|---|
| F1 | Discovery proposed `light.set_brightness` for every light, also on/off-only ones | low | **fixed** |
| F2 | Home Assistant answers **success** to a call on an entity it does not have. Chitala stayed safe; a config typo shows only as `unconfirmed` outcomes | low | **fixed** (Project Lead's rule: only on a live inventory) |
| F3 | A real AI could not use a right delegated again: the MCP broker (and `chitala intent`) attached the first token naming the right, **expired or not** | medium | **fixed** |
| F4 | After its token was revoked, Chitala presented it about 6 times a second. Home Assistant counts each as a failed login, and with `login_attempts_threshold` set it **bans the address for good** | medium | **fixed** |
| F5 | The node observes a device whose last observation failed again on every tick (1 s), without backoff | low | **fixed** (Trusted Core; Safety unchanged) |
| F6 | A device Home Assistant reports `unavailable` keeps its last state as **fresh**, and Safety admitted a high-risk unlock on it | medium | **fixed** (Trusted Core, core-freeze exception granted by the Project Lead) |

## Findings

### F1: discovery and brightness (fixed)

`chitala ha-discover` proposed `light.set_brightness` for every light. Home Assistant's rule is that a light dims when one of its `supported_color_modes` is not `onoff`. Discovery now follows it, and a light that declares no color modes is not assumed to dim.

- **Tests:** `discovery_proposes_brightness_only_for_lights_that_have_it`.
- **Mutations:** 3, all caught.

### F2: Home Assistant answers success for an entity it does not have (fixed)

A service call on a missing entity returns success over WebSocket, and HTTP 200 `[]` over REST, while nothing runs. This is why Chitala never takes "success" as the outcome. In the first pass:

- a door mapped to a missing entity was refused by Safety, because its state is unknown;
- a light reached `unconfirmed`.

**Project Lead's rule.** Refuse before sending only on authoritative evidence from a live Home Assistant. Never infer absence when the link is down, before its inventory, or when the inventory is uncertain.

**Fix.** The link knows whether Home Assistant has an entity only when all of these hold:

- the link is live;
- `get_states` succeeded on this very connection;
- the entity was neither in that inventory nor reported since, or Home Assistant reported it removed.

Otherwise the link knows nothing. A command to an absent entity is refused before sending (`X_ADAPTER`, certainly not executed), and observing it costs no REST read. A `get_states` that fails no longer reads as an empty inventory. The fake Home Assistant now answers a call on a missing entity as the real one does.

- **Tests:** four in `ha_tests.rs`:
  - refused, and present again once it appears;
  - absent again once removed;
  - absent by a new connection's inventory;
  - never inferred without a live inventory.
- **Mutations:** 8, all caught.

### F3: the AI's token choice (fixed)

Alice delegated a right again after its token had expired. The AI was still refused "token expired", because the broker took the first token in the file that named the right. A request that no token named was refused "token expired" too, for the same reason.

**Fix.** The broker and `chitala intent` choose in this order:

1. a token valid now on the exact resource;
2. a token valid now on a scope;
3. the same two, expired or not valid yet;
4. any other token.

The full rule is in spec 12.

- **Tests:** four in `chitala-mcp/tests/broker.rs`, one in `chitala-cli`.
- **Mutations:** 7, all caught.

### F4: a rejected token presented again and again (fixed)

Home Assistant counts every request with a rejected token as a failed login. With `ip_ban_enabled` and `login_attempts_threshold` set, which is a common hardening, it bans the address and writes the ban to `ip_bans.yaml`. Only the Supervisor's address is exempt. The node observed every Home Assistant device once a second by REST, so a revoked token meant about six failed logins a second.

**Fix.** The link and REST share an `AuthGate`:

- it closes after a rejection (`auth_invalid`, or 401 on a read);
- it reopens after 5 s, doubling up to 10 min;
- in between, every request is answered at once with `X_ADAPTER`, and nothing is sent.

In the lab, through the proxy, the link presented the token at 0, 5, 15 and 35 s, and REST sent nothing.

- **Tests:** four in `ha_tests.rs`.
- **Mutations:** 7, all caught.

Home Assistant logged none of the link's failed logins. It answers `auth_invalid` first and only then records the failure, and the link closes the connection at once. Nothing should rely on that ordering.

### F5: failed observations are retried every second (fixed)

`Node::due_observations` picked a device whose last report was older than half its allowed age. A failed observation recorded nothing, so the device was due again on the next tick, once a second, for good.

**Fix (Project Lead's schedule).** After a failed observation the periodic pass asks again after 1, 2, 4, 8 and 16 s, then every 30 s. A good observation resets it to 1 s.

- **Safety is unchanged:** the state is unknown meanwhile (F6).
- **Pending outcomes are not delayed:** the witness of a pending outcome is still asked on every pass. Otherwise the wait could turn `verified` into `unconfirmed`.

**Tests.**

- A counting adapter shows the attempts at 1, 3, 7, 15, 31, 61 and 91 s instead of every second.
- The device is seen at the next attempt once it is back.
- The pace starts over after a success.
- A pending witness is asked on every pass.

**Mutations:** 7, all caught. The property test of random faults, crashes and restarts ran 150 seeds, green.

### F6: an unavailable device keeps a fresh state (fixed)

Home Assistant reported the front door lock `unavailable`. Chitala's twin kept `locked: true` with freshness `fresh`, adding only an `observe_error`, and `SAFE-3` admitted Alice's unlock, a high-risk action. This followed spec 10 to the letter, so it was a gap in the design.

**Project Lead's invariant, for every adapter.** Losing current observability makes the last known state history, not evidence.

**Fix.**

- **The twin.** It keeps the last known state and records since when the device cannot be observed. Any failed observation sets this:
  - the periodic pass;
  - `read_state`;
  - start-up;
  - the witness after an order.

  Only the next good observation clears it, never an older one.
- **Safety** reads only the current evidence, so `SAFE-3` refuses medium and higher risk actions meanwhile: fail closed.
- **`read_state`** shows the last known state with `freshness: unknown` and `unobservable_since_ms`. The approver no longer sees "locked".

The Matter adapter will report an unreachable node, a lost subscription or a stale attribute through the same path.

**Tests.**

- Locked, then unavailable: the unlock is refused.
- Back but not looked at yet: still refused.
- Observed again: allowed.
- Also covered: the periodic pass, a failed reading, a witness after an order, and the whole chain on the fake Home Assistant.

Two older tests had assumed the gap: a device the node knew to be offline still counted as fresh. They now take the device offline without the node noticing, which is what they meant.

**Mutations:** 11, all caught.

**F9: the decision and the fix.** The Project Lead set the invariant (2026-10-05):

> Outcome evidence must prove that the state was produced, or changed, after the order could have acted. Chitala reading the state after the command is not enough.

The first proposal was weaker: it compared with the time Chitala *received* a state. That would not have fixed F9, because the twin recorded the receiving time and the Home Assistant adapter dropped `last_updated`. The fix:

- **Every observation carries its age.**
  - A device read now has age 0 (the virtual devices).
  - A state the Home Assistant link heard pushed is aged from when it was heard.
  - A state from the link's bootstrap has no age anyone can tell.
  - A REST read is aged by Home Assistant's own clock (`Date` minus `last_reported`, plus a second for `Date`'s rounding).

  The node computes `source_at = received_at − age` and keeps it in the twin.
- **Every order carries its send time**, persisted at mint.
- **An observation settles an outcome only if `source_at ≥` the send time.** Otherwise it is history. With no evidence by the deadline the outcome is `unconfirmed`, never `not_applied`, and at medium risk or more the resource goes into recovery.
- **Tests:**
  - the red test `a_cached_state_from_before_the_order_never_settles_an_unknown_execution`;
  - the crash points C and D, which now settle only on a report after the order;
  - a lock whose answer is lost and which moves a second later, and still ends `applied`;
  - the adapter's ages;
  - nine mutations, all caught;
  - the property test over 150 seeds.
- **The cost:** a command that changes nothing (locking a locked door) leads to no new report through Home Assistant. Its outcome is therefore `unconfirmed`, and for a lock, recovery. So is a fast change carried by REST, while the link is reconnecting.

**Found while checking the fix on the real Home Assistant:** MT5a still ended `not_applied`. Watching Home Assistant's own events showed why:

```text
21:28:36  the Matter lock dies
21:28:41  unlock sent; Home Assistant writes `unlocking` at once (its optimistic state, not the lock's)
21:29:11  Home Assistant writes `locked` again (its cached value), with a new last_updated and a new context
```

Two things followed from this:

1. **Fixed: a state in motion is no answer.** `unlocking` postdated the order, so it counted, and at the deadline "observed, not as expected" read as `not_applied`. Now `not_applied` needs the witness to report a **settled** state, every promised key. In motion or at fault, the outcome is `unconfirmed`.
   - Red test: `a_lock_still_moving_at_the_deadline_is_not_known_to_have_failed`.
   - 2 mutations, both caught.
2. **F9b: Home Assistant re-emits a cached value as a fresh state.** When a lock does not confirm a lock or unlock command, Home Assistant reverts its optimistic state to the value it held, with a new timestamp, 30 s later (the optimistic timer of `homeassistant/components/matter/lock.py`; an earlier reading of this report said 5 s after a lock, which holds only for `open`). Through Home Assistant's states, Chitala cannot tell that revert from a report by the device, and the context id does not tell either. Fixed; see below.

The admission window remains too: Safety trusts Home Assistant's served state until it says `unavailable`. Option C closes it in step ⑤.

**F9b: the decision and the fix.** The Project Lead's invariant (2026-10-05):

> A gateway-generated timestamp is not physical freshness. A post-command observation is admissible only if the adapter can also establish current reachability/provenance of the underlying device.

The logic stays in the Home Assistant adapter's Matter path. The core only gets metadata, and its outcome engine trusts only a confirmed state (spec 22, *Evidence must be confirmed current*):

- **Every observation carries a provenance:** `ConfirmedCurrent { age_ms }` (the adapter reached the device that long ago, no earlier than the state) or `Uncertain`. The node keeps `confirmed_at` in the twin. An observation is evidence only if `confirmed_at ≥ source_at ≥` the order's send time.
- **The node asks for evidence only when it needs it:** right after an order that may have executed, and for the witness of a pending outcome. Safety's observations never cause an exchange with a device.
- **How the Home Assistant adapter confirms a Matter device:**
  - It reads the entity registry on every connection, to learn which entities are Matter devices and their device ids.
  - It asks such a device through `matter/interview_node`, which reads the device's attributes. The probe showed a Read request in the device's log; the answer came in 0.02–0.05 s, and a dead device's failed after about 15 s.
  - A state is confirmed only if an exchange that **began after** the link heard it succeeded.
  - The adapter waits for an answer for 1 s at most. One exchange runs at a time; a device that failed is asked again after 5 s at the earliest.
- **`matter/ping_node` was rejected.** It is an ICMP ping of the device's addresses, and it answered `true` for the lock whose process was dead (shared host addresses in the lab). It is no liveness proof. The Lead allowed for this: *interaction success tied to that endpoint is better than a bare ping.*
- **Tests:**
  - the red test `a_dead_matter_lock_s_cached_state_with_a_new_timestamp_is_no_evidence`, which ends `not_applied` under the old rule;
  - the positive case `a_live_matter_lock_s_fresh_state_settles_its_outcome` (`verified`, `applied`, `not_applied`);
  - the core rule with a mock adapter, across a restart too;
  - the adapter's provenance, the host protocol, and the process boundary;
  - 17 mutations, all caught.
- **On the real lab (MT8),** with the build before the fix: when the node was down before the deadline and back 15 s later, the restored outcome's window covered the revert, and the outcome was **`not_applied`, without recovery**. With the fix: `unconfirmed` and recovery.

The Project Lead's decisions on what remained (2026-10-06):

- **When F9b bites.** With the lock's `within_ms` (5 s) and the link's call timeout (10 s), the 30 s revert lands after the deadline in steady operation. It falls inside the window after a node outage across the deadline, as in MT8, or with a longer `within_ms`. The fix covers every case.
- **Other integrations keep Home Assistant's word: kept, as a lower assurance.** A non-Matter integration that writes a cached value with a new timestamp can still settle an outcome. Strict `Uncertain` for every non-Matter entity would leave every such lock in recovery after every command. That confirmation is the gateway's word, not physical proof. Confirmations per integration, where a risk class needs them, come later.
- **An administrator's token for Matter evidence: accepted for ③A, as a deployment requirement** (spec 25). It is one more reason for the direct Matter adapter (step ⑤), which needs no Home Assistant administrator.
- **REST only (`websocket: false`) is a degraded mode, not an equivalent one.** It can serve observation, history and, as policy allows, low-risk operations. It never gives confirmed evidence, and outcomes through it end `unconfirmed`.
- **The proof relied on Home Assistant's order: finding F10, now fixed** (below). An attribute the interview finds changed reaches the link as a newer state, and so needed a newer answer. That assumed Home Assistant sends that state before the interview's result, and the lab showed it does not always.

**F10: the investigation, the decision and the fix.**

*Step 1, the order of things (Project Lead, 2026-10-06).*

- **The source.** Home Assistant's side keeps the order:
  - its Matter client applies events before it resolves a command;
  - an entity writes its state synchronously;
  - the WebSocket connection to Chitala is a queue.

  The Matter server keeps it only while a connection is not congested. Past 1 MiB waiting, it queues attribute and node updates but sends command results at once ("jumping the queue is harmless", `WebSocketConnection.ts`). And Home Assistant's `matter/interview_node` returns no data.
- **The lab.** A client did what Chitala's link does. A second listener sat on the Matter server, and the lock's own log showed when it changed and when it served the Read.

  | Situation | Rounds | The interview succeeded while the client held the old state |
  |---|---|---|
  | Normal; the lock changed −40 to +60 ms around the interview | 80 | 0 (34 changed before the Read; their `state_changed` came 38–133 ms before the result) |
  | Two interviews at once | 40 | 0 |
  | **Backpressure**: Home Assistant paused 3 s, the server flooded with about 300 interviews, the lock changed 300 ms before Home Assistant's interview | 6 | **3**. In all 6, Home Assistant then dropped and reopened its connection to the server |
  | The Matter server killed during the interview | 3 | 0: Home Assistant never answered |

- **The conclusion.** The order is usual, not guaranteed, so an interview's success is no confirmation. No fence through Home Assistant is sound:
  - it exposes no read values and no sequence;
  - every command result jumps the server's queue;
  - a write of another attribute can pass any fence while the changed one waits.

*The fix: the `MatterEvidenceProvider`.* The Matter server's `read_attribute` is a Read interaction with the device, and it answers with the values. In the lab it took 3–10 ms, and it was right 5 ms after a change; a dead device gets no answer. For evidence, the Home Assistant adapter now reads a Matter device itself (spec 25):

- **Narrow.**
  - Read only: `read_attribute` is the only command it can send.
  - Allowlisted: the profile's attributes only.
  - On this machine only, because the Matter server's API has no authentication.
  - A bridge toward step ⑤.

## Home Assistant facts worth knowing for ③B

- **The `http:` block is on trial.** Since 2026.9 it is moved into storage as a config on trial. Unless it is confirmed (`http/config/promote`) within five minutes, Home Assistant reverts to listening on every interface and restarts. The lab's bootstrap confirms it.
- **A Demo lock's call returns only once the lock has moved**, about 2 s later. Physical locks and their integrations may answer before the state changes. That is what `pending` and `within_ms` are for.
- **Running `hass` directly**, a restart is an exit with code 100, and something must start it again (`run_hass.sh`).
- **Home Assistant 2026.9 on Python 3.14 (macOS) can segfault** while the interpreter exits after a restart request (exit code 139 instead of 100, in `finalize_modules`). A supervisor has to restart it after a crash too. The lab's does.
- **Behind a reverse proxy.** If a proxy in front of Home Assistant stays up while Home Assistant is down, a REST command reaches the proxy before the connection breaks. Its fate is then unknown (`X_EXECUTION_UNKNOWN`), not "not delivered". Chitala is right to say so: it cannot tell whether the proxy passed the command on. Consequences:
  - a light's outcome ends `unconfirmed`;
  - a door is refused by Safety, because its state cannot be observed (F6).

  For ③B, connect to Home Assistant directly, or make the proxy refuse connections while Home Assistant is down.
- **Safety's rate limit** (`SAFE-6`, three actuations of a door per minute) also applies to a test run. The regression waits between scenarios that move the same door.
